# Architecture

Kernel version 0.1.0. This document records the design decisions behind the kernel and the compiler checks, and the reasons for each.

## 1. Why a type system rather than first-order logic

The Amsterdam program of the 1990s translated organization theories into first-order logic and ran theorem provers over the result. First-order logic is undecidable: a prover reporting no contradiction after a bounded search leaves consistency open, and each theory lived in a private vocabulary, so two formalizations could not be checked against each other.

Lemma makes two different commitments.

1. **Every question the compiler answers is decidable by construction.** Reduction (Q1) is a finite traversal of a structure's fields. Overlap (Q2) is a finite comparison of leaf sets. Scope (Q3) is a finite search over registered rules. Composition (Q4) is a finite pass over registered propositions. None of these invokes a theorem prover over an open domain. Where the kernel needs a proof obligation (an aggregation must raise the level, a temporal rule must lengthen the horizon), the obligation is a closed proposition over an enumeration discharged by `decide`.
2. **One vocabulary.** Every construct in every theory module reduces to the same registered primitives at the same enumerated scopes. Two theories formalized by different people compose because they are forced into the same leaf space. The price is that the leaf space, the primitive vocabulary, is a methodological commitment. It is versioned and reviewable, and the proposal lists it under risks.

Lean 4 is the host because its elaborator is programmable: the checks are attributes and commands that run while a file compiles, the registries persist across modules in `.olean` files, and a type without an `IsConstruct` instance cannot enter a proposition, so enforcement is by the type checker rather than by a separate linter pass.

## 2. The kernel

`Lemma/Kernel/` has five construction rules and zero psychological content.

| Rule | Lean object | What it fixes |
|---|---|---|
| 1 Observation | `structure Observation` (level, horizon, source, unit id, time index, value); `ObservationBundle level horizon` with a proof that every observation carries the bundle's scope | A measurement event and the scope it belongs to |
| 2 Construct | `structure Primitive` (the base of value types); `structure Construct (level) (horizon)` (empty, scope in the type parameters); `class IsConstruct C` (level, horizon), generated by `@[construct]`; `class Measures C` (bundle → value) | A construct is a function from observations at a scope to a typed value |
| 3 Aggregation | `structure Aggregation A B [IsConstruct A] [IsConstruct B]` with `rule`, `citation`, and proofs `raisesLevel`, `keepsHorizon` discharged by `decide` | An explicit map across levels |
| 4 Temporal | `structure Temporal A B` with `lengthensHorizon`, `keepsLevel` by `decide` | An explicit map across horizons |
| 5 Proposition | `structure Proposition A B [IsConstruct A] [IsConstruct B]` with `direction`, `level`, `horizon`, `boundary`, `evidence`, `citation` | A typed relation |

Enumerations: `Level` (Individual, Dyad, Team, Unit, Organization), `Horizon` (Momentary, Daily, Weekly, Monthly, Annual, Static), `Source` (SelfReport, OtherReport, Sensor, Administrative, Behavioral), `Direction` (Positive, Negative, Null, Curvilinear), `EvidenceKind` (Experimental, Longitudinal, CrossSectional, MetaAnalytic, Simulation, None), `Boundary` (none, moderator with a `ModerationEffect` of Buffers / Amplifies / Conditions, scope description).

**Enforcement of reduction.** `IsConstruct C` has no user-written instances. The `@[construct]` attribute runs the reduction, and only on success adds `C.instIsConstruct`. `Proposition A B`, `Aggregation A B`, `Temporal A B` and `Boundary.moderator M` all demand the instance, so an unreduced type cannot appear in any kernel relation. `LemmaTests/Reduction.lean` pins the error.

**Decidable rule constraints.** `Aggregation A B` carries `raisesLevel : (levelOf A).rank < (levelOf B).rank := by decide`. The instances generated by `@[construct]` are reducible definitions, so `decide` evaluates the ranks and rejects a rule which lowers a level at the definition site. `LemmaTests/Scope.lean` pins the error.

**Static embedding.** A construct at `Horizon.Static` is a constant function of time and embeds into any horizon at its level. A trait can enter a weekly proposition without a temporal rule. This is the one asymmetry in scope matching, and it is in `Lemma/Meta/Scope.lean`.

## 3. Primitives are library, not kernel

The kernel requires that a construct reduce to registered primitives. It does not say which primitives exist. `Lemma/Library/Primitives.lean` declares the pilot vocabulary (`Energy`, `Attention target`, `Identification target`, `Demand kind`, `Resource kind`, `Change kind`, `Affect valence activation`, `Learning`, `Efficacy target`, `Motivation kind`, `Skill`, `Symptom kind`, `Performance kind`, `Intention kind`, `Trust target`, `Expectancy valence`, `Behavior kind`, `Trait kind`).

Two design rules follow.

- **Primitives are concrete, abstractions are constructs.** "Job resources" is a bundle of `Resource Autonomy`, `Resource SocialSupport`, and so on, not a primitive `Resource Generic`. Containment between abstractions (ERI reward inside COR resources) then shows up as leaf-set inclusion, which the overlap check reports as `subtype`.
- **Primitive arguments are atomic.** `Identification Work` and `Identification Organization` are different leaves. The kernel has no subtyping among arguments. This is a known limitation: a construct built from `Demand Workload` does not overlap one built from `Demand Generic`, which is why the pilot vocabulary has no `Generic` kinds.

Primitives are unsigned. Exhaustion and vigor both read `Energy`; the construct's docstring says which pole it reads, and propositions carry the sign. The compiler reports exhaustion and vigor as an identity overlap, which is the point: whether they are opposite poles of one continuum is an empirical question the library records as a declaration plus a correlation.

## 4. The four checks

All checks live in `Lemma/Meta/` and run in `MetaM` inside the elaborator.

### Q1 Reduction (`Reduce.lean`)

`reduceConstruct C` weak-head-normalizes `C` and walks it. A registered primitive becomes a leaf `(prim, args, path, via, level, horizon)` with the scope of the nearest enclosing `Construct l h` ancestor. A registered construct contributes its stored leaves (prefixed by the path) and is recorded as a component. A structure is unfolded only when it is `Prod` or descends from `Construct`; any other structure, any axiom or opaque constant, and any non-constant head is a failure with a reason. A composite `def` inherits the unique scope of its leaves and is rejected if leaves disagree.

### Q2 Overlap (`Overlap.lean`)

The key of a leaf is `(prim, args, level, horizon)`. For a construct `A` against every registered `B` (components excluded): shared keys non-empty means overlap. Kind is `identity` when the key sets are equal, `subtype` when one is a proper subset, `partial` otherwise. Shared primitive with different scope is a **scope shift**, reported separately as a place for a temporal or aggregation rule. The warning text begins `shares primitive X with B.field`, as in Listing 1 of the proposal. `declare_overlap A distinct_from | alias_of | subtype_of B "reason"` records a resolution; the command warns when the declared kind does not match the computed kind (`alias_of` on a partial overlap).

### Q3 Scope (`Scope.lean`)

For each construct of a proposition, `routeConstruct` tries: exact scope (with static embedding), then an aggregation to the declared level followed by a temporal rule to the declared horizon. Success is `exact` or `routed [rule names]` (logged as info); failure is an error naming the missing rule. Moderators are not scope-checked: a static trait or a daily recovery experience may moderate a weekly relation.

### Q4 Composition (`Compose.lean`)

Two propositions are comparable when they share antecedent, consequent, level, horizon and boundary. Comparable propositions with contradicting directions (`Positive`/`Negative`, or `Null` against a signed direction) are a contradiction: a warning across theories, an error within one. Exactly one curvilinear direction is a shape disagreement. The Python layer adds **conditional disagreements** (contradicting directions under different boundaries) and **convergences** (same claim in two or more theories).

Implied propositions come from unconditional chains `A → B`, `B → C` at one scope with `A ≠ C`, composed by the sign algebra (`+∘+ = +`, `+∘− = −`, `Null` and `Curvilinear` undefined). Each is `tested` if a registered proposition states the pair at that scope, `contradicted` if the registered direction contradicts the implied one, `untested` otherwise. Length-2 only: longer chains add nothing at pilot scale and multiply path counts. The implied sign is a path sign, not a total effect, so the agenda labels it a candidate.

### Cross-level propositions

The kernel has no top-down relation. A unit feature affecting individual behavior is stated at the unit level over the aggregate of the behavior (`Lemma/Theories/Thriving.lean`, Spreitzer et al. 2005). The crossover paper in the pipeline fixtures fails for this reason, and the failure is recorded with the reason. A `Contextual` rule is planned for kernel 0.2.

## 5. Registries and the report

Each kind of entry (primitive, construct, proposition, aggregation, temporal, overlap declaration) is a `SimplePersistentEnvExtension` of plain data, serialized into `.olean` files and merged on import. A theory module compiled in one file is visible to checks in another. The theory tag of an entry is the last component of the module name in which it was declared (`Lemma.Theories.JDR` ↦ `JDR`), which keeps the mapping from theory to file explicit.

`#lemma_report "path"` dumps every registry and every check result as JSON. `scripts/report.lean` imports the library and the accepted generated modules and runs it; `lemma check` regenerates its import block and reads the JSON back.

## 6. Scorer

`pipeline/lemma/score.py`, weights in `config/scoring.yaml`.

```
score(p) = w_e·E(p) + w_s·S(p) + w_g·G(p) + w_i·I(p)        (weights sum to 1)
E(p) = evidence_weakness[strongest evidence kind across comparable propositions]
S(p) = min(1, (theories asserting p + implied propositions with p as premise) / saturation)
G(p) = max over disagreements p takes part in (contradiction 1.0, implied contradiction 0.8, conditional 0.6, shape 0.5)
I(p) = 1 for an implied-untested candidate, else 0
```

For an implied candidate, `E = 1`, `S = min(1, (theories joined − 1 + mediating paths) / saturation)`, `G = 0.8` when another composition implies the opposite direction. One agenda entry per claim: comparable propositions from several theories collapse into one entry listing all of them. The agenda has a combined table and separate tables for registered claims and implied candidates, because the two kinds answer different questions.

## 7. Versioning

`KERNEL_VERSION` is `0.1.0`. Any change under `Lemma/Kernel/` bumps it and gets a `CHANGELOG.md` entry. Changes to the primitive vocabulary (`Lemma/Library/Primitives.lean`) bump the library minor version and are logged in the same file. Reports record the kernel version they were produced with.
